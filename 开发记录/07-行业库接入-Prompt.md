# 07 · 行业库接入 Prompt（电商演示数据 → Supabase）

四轮分开做，一轮确认后再贴下一轮。密钥向用户要，不要写进仓库。不改平台代码、不打镜像、不起 Compose。业务库统一放 dw schema（DW_SCHEMA，默认 dw），app schema 是会话/报表、启动自动建，本轮不碰。

---

## 第 1 轮 · 只设计库表，先别造数、先别连库

```
下面只做电商演示库的表结构设计，不要生成 INSERT、不要连 Supabase、不要改问数链路代码。

先读：
- docs/测例.md（当前版本是 T01-T15，按这份的编号与含义来，别用旧的 T01-T13 口径）
- docs/metrics-dictionary.md
- docs/SDD-后端.md 第 4、5 节（存储设计 / 数据层与可答范围）
- docs/SDD-算法应用.md 第 7.2 节（业务数据库）

当前仓库没有旧的 data-init 五表玩具库，backend_service/db/01-init.sql 只建 schema/角色/扩展。本轮新建文件落 backend_service/data-init/（已拍板），不存在「在旧五表上修修补补」的问题；也不要去改 algorithm 包（它的离线 Mock schema 只在 algorithm/tests/mocks/，仅供测试）。

约束：
1. 这是通用 ChatBI，电商大促复盘只是拿来验收的场景。表放在 PostgreSQL 的 dw schema，不要放进 app schema，不要写到 public。
2. 表集以 metrics-dictionary v0.2 §5 拍板为准：3 维（dim_date 含档期列、dim_channel、dim_category 两级）+ 3 事实（fact_order 含 is_new_customer、fact_order_item 含退货列、fact_traffic_daily 日×渠道 UV）。不另建客户表（新老客用 fact_order.is_new_customer）、不另建门店/活动表（运营资源即 dim_date 档期列 + §4.1 命名区间，本版不接第二张运营资源表）。不要做成生产级电商中台：禁止仓配、SKU 实时库存、结算对账、会员积分、完整 OMS。
3. 转化率口径以 metrics-dictionary v0.2 拍板为准：支付转化率 = 支付买家数（去重客户）÷ 访客数（UV），分母来自访问/流量事实表，不是「已支付订单 / 全部订单」（那是支付成功率）。对照表要写清分子分母各自用哪张表、哪几列。
4. 必须能支撑当前测例：渠道 GMV（T01/T03/T08/T12）、转化率（T02）、类目退货率与退货金额（T04/T05）、AOV（T06）、档期（T07/T11）、新老客（T13）。时间窗必须都能从日期列切出来，不要只靠一个 is_promo 布尔：
   - 今年 618 正式期 = 2026-06-16~2026-06-18；去年同窗 = 2025-06-16~2025-06-18
   - 档期三段 = 预热 2026-06-01~06-15 / 正式 06-16~06-18 / 返场 06-19~06-20（去年 2025 同窗）；「618大促期间」整体命名区间 = 当年 6/1~6/20
   - 大促前一周 = 2026-06-09~06-15；大促后一周 = 2026-06-19~06-25（T07 独立切窗，与预热/返场重叠没关系）
5. 不要建 SKU 级实时库存 / 库存周转表；品牌心智、归因类在库里就该无对应数据（T10/T15 靠这个拒答）。
6. 每张表、每列写中文 COMMENT。低基数枚举列（渠道、订单状态、支付状态等）值要稳定、可采样。类目列 DISTINCT 取值 ≤20（L0 枚举采样只收 ≤20 的列，「美妆」多候选是 T09 澄清的触发前提）。主键、外键、建议索引（时间、渠道、类目、门店）。这是给 L0 自动抽库结构用的。

交付（等人确认后再进入第 2 轮）：
- 一份 ER 说明（表职责 + 关系，中文）
- 完整 DDL（CREATE TABLE + COMMENT；schema/角色已有不用重建），覆盖写入 backend_service/data-init/，不要执行
- 一张对照表：T01-T15 各自主要查哪几张表、靠哪些字段算（T02 标转化分子分母；T09 标「美妆」怎么造成多候选；T10/T15 标「无对应数据」；T11 标档期三段怎么切；T13 标新老客怎么切）
```

**人审要点**：转化分母、档期三段、美妆多候选、新老客这四块缺了不算「表过重该砍」；该砍的是仓配/库存/结算。检查 T09/T10/T11/T13 有没有设计歪；有没有误写入 app / public 或实时库存。

## 第 2 轮 · 按已定表结构准备种子数据，仍不连库

```
第 1 轮表结构已经确认。现在只准备可导入的模拟数据，不要连 Supabase，不要改问数链路代码。新写种子文件按导入顺序编号落 backend_service/data-init/，仓库里没有旧种子，不要自己脑补一份去沿用。

要求：
1. 严格按已确认的 dw schema DDL 生成种子数据（SQL INSERT 优先）。
2. 年份钉死：今年 = 2026，去年 = 2025。数据至少覆盖 2025-06-01~2025-06-25 与 2026-06-01~2026-06-25，不要写成 2024 或其它年。
3. 数据必须让 docs/测例.md 的 T01-T15 在「库里有数」这个层面站得住：
   - T01：多个渠道（≥4），正式期分渠道 GMV 能排出明确高低，不要并列第一
   - T02：真转化口径（访客数 UV 分母 + 支付买家数去重分子，不要用支付成功率冒充），能按渠道算出并排出最高
   - T03：2026-06-16~18 分日分渠道 GMV，三天都有数、能看趋势；这份分日数据同时支撑 T12 的按天展开
   - T04 / T05：正式期分类目退货率能取 Top3；至少一个、建议多个类目退货率超过 8%，且退货金额能加总；「美妆」退货率相对 8% 阈值方向明确
   - T06：AOV 在正式期有足够订单，分母口径（订单数或付款人数）与库内数据自洽，别两种都能算却互相打架
   - T07：前一周 / 正式期 / 后一周 GMV 三窗都有数、能看出变化
   - T08：2026 vs 2025 同窗整体 GMV 涨跌明确、差额可算
   - T09：「美妆」在类目列/层级上命中 ≥2 个可匹配候选（如「美妆」「美妆/护肤」「美妆/彩妆」），能触发澄清而不是硬猜
   - T10：不造品牌心智/份额类数据
   - T11：预热/正式/返场三档期 GMV 都非 0，能按档期切出三段、占比可讲
   - T13：新客、老客 GMV 都非 0，占比能算
   - T14：分类目 GMV TopN 可取
4. 时间、状态、金额口径要自洽（笔数不超过支付、明细合计对得上主表、退货数量不超过购买数量）。
5. 转化形态：访问量必须明显高于下单量，转化率应是百分之几到二十左右，禁止接近 100%。
6. 体量（宁可偏多，不许偷减压成玩具库）：
   - 下限：订单主表至少约 5000 行，订单明细相应更多（一单一到多行）；访问/会话事实按日

交付：
- 种子 SQL 文件（按导入顺序编号，落 backend_service/data-init/）
- 每表预计行数清单
- 一份自检说明：T01-T15 每条靠哪些数据立住，缺哪条补哪条
```

**人审要点**：体量有没有被压到几千以下；年份是不是 2025/2026；档期三窗、转化分母、美妆多候选、新老客有没有空；转化率会不会假到接近 100%；数字会不会自相矛盾。

## 第 3 轮 · 在 Supabase 建 dw 业务表并导入

```
设计和种子已经确认。现在把电商演示库建到我的 Supabase Postgres 的 dw schema 里，并导入数据。

范围：
- 只操作 dw schema 的业务表和种子数据
- 不要动 app schema（09 轮才初始化），不要在 public 建业务表，不要配 pgvector、不要建任何 YAML 资源
- 不要 Docker Compose、不要打镜像

请先向我要这些（缺一就停，不要猜）：
- Supabase 项目是否已建好
- **Transaction 池化**连接（免费档直连 5432 不可用）：Host 一般是 *.pooler.supabase.com，端口 6543，用户一般是 postgres.<project-ref>，库名 postgres，sslmode=require。不要再向用户要 db.xxx.supabase.co:5432

然后按这个顺序做：
1. 用我提供的凭据连上（可用 psql、官方 CLI 或临时脚本；密钥只用于本机执行）
2. URI 不要混用：psql 用 postgresql://...:6543/...；后端 .env 的 APP_DATABASE_URL / ANALYTICS_DATABASE_URL（09 轮填）也用 postgresql:// 同一条池化串（引擎内部自动转 psycopg3 驱动）。已拍板：两个 URL 都用同一 postgres 串。Transaction 模式不支持预处理语句（psycopg 的 prepare_threshold=0，09 轮统一改 engines.py），导入时若报 prepared statement 错就按这个方向处理
3. 按既定顺序在 dw 建业务表
4. 按既定顺序导入种子
5. 列出 09 轮我需要填的变量名：APP_DATABASE_URL、ANALYTICS_DATABASE_URL（都填同一条 Transaction 池化串，带 sslmode=require）、APP_SCHEMA=app、DW_SCHEMA=dw。告诉我怎么填；不要把真实密码写进仓库文件
6. 做完列出：在远端实际执行了哪些语句类别、导入了哪些表、每表大约多少行。
7. 若连不上或权限不够，把报错原文给我，给出下一步要我做什么，不要改方案绕过。
```

**人审要点**：连的是不是目标项目、是不是 6543 Transaction 池化；有没有误写 public 业务表；有没有顺手去动 app schema 或配向量；密码有没有被提交进 git。

## 第 4 轮 · 验证库是否可用（只验库，不跑完整 ChatBI）

```
数据已经导入 Supabase。现在只验证「这张库能不能当问数数据源」，不要启动整站、不要打镜像、不要改算法。

不要按 docs/测例.md 一条条写业务 SQL（不要写 GMV、转化率、退货率、AOV 的计算公式）。测例是给 ChatBI 问句用的，口径归 L0/L1 和 Coder，本轮替产品拍口径没有意义。本轮只查目录、注释、枚举、行数、日期覆盖、关联是否断、禁止表是否存在。

请用只读检查，把结果用表格或简短文字回给我：

1. 连通：列出 dw schema 下全部表名；public 下不应出现这批业务表；app 下这轮不应有东西
2. L0 友好：pg_catalog / information_schema 能读到列类型；每张表、每列 COMMENT 能读到（缺注释的列列出来）；渠道、类目、订单状态等低基数列能 DISTINCT 出枚举；类目列 DISTINCT ≤20 且「美妆」能命中 ≥2 个候选
3. 行数：每张表 count(*)，空表标出来；订单主表应至少约 5000 行
4. 结构齐（对照第 1 轮已确认的 ER，只查「有没有、挂没挂上」，不算指标）：
   - 有转化分母表（访问/会话事实），且能和订单在日期、渠道上对上；不要只凭订单状态列声称能算转化
   - 有档期依据：dim_date 的档期列（预热/正式/返场/日常）能切出三段（本版运营资源即档期日历，不接第二张运营资源表）
   - 有退货相关列或表（数量或金额）
   - 有新老客依据（首单时间或等价标记）
   - 没有 SKU 实时库存 / 库存周转、品牌心智类表（T10/T15 就该无对应数据）
5. 时间覆盖（只查日期列的 min/max 和各窗行数，不算金额）：订单和访问在正式期、预热、返场、前一周、后一周、2025 同窗都不能空
```

**人审要点**：有没有偷偷写成 T01-T15 业务 SQL；探路是否真的查了远端；库存/品牌心智是否仍无表；转化分母表、美妆多候选是否真实存在。
